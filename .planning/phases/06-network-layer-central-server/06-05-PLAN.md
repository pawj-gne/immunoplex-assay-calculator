<task type="checkpoint:human-verify" gate="blocking">
  <what-built>
Windows .exe installers for Phase 6 (v0.7.0) are built. The app now has a three-mode network layer: local-only (no config.json), server mode (isServer:true), and client mode (isServer:false). The full automated test suite is green on macOS.

This checkpoint verifies the network layer end-to-end on real Windows hardware with two lab PCs.

**Deployment steps before verification:**

1. **Download installers** from GitHub Actions artifact or from `dist/` on the macOS dev machine.

2. **Install on all lab PCs** — run `immunoplex-assay-calculator-0.7.0-x64-setup.exe` on each machine.

3. **Create config.json on each machine** at:
   `C:\Users\{username}\AppData\Roaming\immunoplex-assay-calculator\config.json`

   Server machine (LAB-PC-01 or whichever is designated):
   ```json
   { "serverUrl": "http://{SERVER_LAN_IP}:3847", "isServer": true }
   ```

   Client machines (all others):
   ```json
   { "serverUrl": "http://{SERVER_LAN_IP}:3847", "isServer": false }
   ```

   To find the server machine's LAN IP: open Command Prompt, run `ipconfig`, look for IPv4 Address under the Ethernet or Wi-Fi adapter.

4. **Launch the server machine first.** When Windows Firewall dialog appears, click "Allow access" — this is required for client machines to reach it over the LAN (RESEARCH Pitfall 1).
  </what-built>
  <how-to-verify>
Perform the following checks on the Windows lab PCs:

**NET-02: Config file and mode detection**
- [ ] Server machine: App launches normally, no "Working offline" banner visible
- [ ] Client machine: App launches, no offline banner visible (optimistic default; server is up)
- [ ] Temporarily rename config.json to config.json.bak on one machine, relaunch — app works as local-only with no prompts (D-03)
- [ ] Restore config.json

**NET-05: Server machine saves go direct (no HTTP hop)**
- [ ] On the server machine, create a new run (full wizard flow). It saves successfully.
- [ ] In the Past Runs list, the saved run appears with the server machine's hostname in the Source column.

**NET-01: Two machines see identical Past Runs list**
- [ ] On the client machine, create a new run. It saves successfully (saves to server via HTTP).
- [ ] On the server machine, open Past Runs — the run created on the client machine is visible.
- [ ] Verify Source column shows the client machine's hostname for the client-created run.

**NET-03: Offline fallback and banner (D-04)**
- [ ] Stop the server machine's app (or disconnect it from the network).
- [ ] On the client machine, within ~10 seconds, the yellow banner "Working offline — saves stored locally" appears.
- [ ] On the client machine, create a new run. It saves successfully (locally). The run appears in Past Runs immediately.

**NET-04: Offline queue flush on reconnect (D-08)**
- [ ] Restart the server machine's app (or reconnect the network).
- [ ] On the client machine, within ~5 seconds (one reconnect poll cycle), the offline banner disappears.
- [ ] On the server machine, the run that was saved offline on the client now appears in Past Runs.
- [ ] Source column on that run shows "{CLIENT_HOSTNAME} — offline save".

**D-02: Conflict display**
- [ ] If two machines created runs with the same request number while one was offline, both rows appear in Past Runs with their respective machine names and timestamps.
  </how-to-verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Windows Firewall → Express server | Windows Defender blocks inbound connections by default; operator must click "Allow access" on first bind |
| LAN → Express server | Once firewall is open, all LAN machines can POST to the server (no auth in v1) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-16 | Denial of Service | Express server port 3847 | accept | If port 3847 conflicts with MSFW-Control on domain-joined machines (RESEARCH Pitfall 5), operator changes port in config.json. Deployment notes in checkpoint instruct operator to check with `netstat -an | findstr 3847`. |
| T-06-17 | Elevation of Privilege | Windows Firewall bypass | accept | The "Allow access" click is a necessary one-time setup step. If a technician clicks "Block", the fix is to re-enable in Windows Firewall settings. Documented in checkpoint instructions. |
| T-06-18 | Information Disclosure | Version 0.7.0 includes Phase 5 schema | accept | The installer ships the Phase 5 master_panels schema. No sensitive data; schema is internal to the lab DB. Migration auto-applies on first launch. |
</threat_model>

## Summary

Phase 15.1 ships three tightly-scoped, well-documented fixes that close the WR-01, WR-02, and WR-06 warnings from `15-REVIEW.md`. The implementation is conservative, additive, and consistent with the patterns established in Phase 15.

**WR-06 (audit-trail completeness) — `auditTrail.ts` + `AuditTrailSection.tsx`:** The three new pure helpers (`computeRawReagentVolumeML`, `computeNewReagentVolumeML`, `computeTotalReagentVolumeML`) correctly compose the canonical calculator pipeline (`calculateTotalWells` → `calculateRawVolume` → `applyOldReagentSubtraction`) against snapshotted `RunRecord` fields. The unit-asymmetry comment block at `auditTrail.ts:71-78` correctly documents the `µL` vs `mL` boundary flagged in RESEARCH. Ceiling-at-last-step (`ceilToTenthML(rawUL)` before `dividedBy(1000)`) matches the live-calculator rule. Null-guard propagation is correct: rawReagent=null → newReagent=null → totalReagent=null cleanly cascades the em-dash placeholder. 14 unit-test cases (`auditTrail.test.ts` Group P) cover happy path, legacy/null, undefined, zero, sample-count=0, and the over-subtract clamp.

**WR-02 (audit-trail integrity) — `useRunSnapshot.ts`:** The three-branch `auditTrailCaptured` gate at `useRunSnapshot.ts:151-178` correctly distinguishes (a) custom-assay (no IPC), (b) IPC-succeeds-with-result, (c) IPC-returns-null, and (d) IPC-throws. The conditional spread on lines 233-244 is byte-correct — when `auditTrailCaptured = false`, all 10 fields (6 master-panel + premixConcentration + 2 override flags + `calculationRulesVersion`) are omitted atomically, which is exactly the "no partial writes" invariant from D-15.1-02. Both diagnostic `console.warn` calls include the master panel ID (lines 168-170 / 174-177) for postmortem traceability. Two new test cases (`useRunSnapshot.test.ts:223-279`) cover the IPC-throw and IPC-null-result branches.

**WR-01 (round-trip fidelity) — `runStore.ts` + `CalculatorForm.tsx`:** The store-side restore at `runStore.ts:164-165` adds `setOldBeadsOverride(run.oldBeadsOverride ?? false)` and `setOldAntibodiesOverride(run.oldAntibodiesOverride ?? false)` to the loadRun cascade, in the correct order (after `setOldAntibodies`, before `plate.loadPlates` — extending Pattern S2 from `14-PATTERNS.md`). The form-side mirror at `CalculatorForm.tsx:91-103` uses the documented incremental-selector pattern (per RESEARCH Open Question 2) to subscribe to the store flags and sync into the local `beadsOverrideAccepted` / `antibodiesOverrideAccepted` React state via `useEffect`. The `?? false` defaulting at both sites is symmetric with the existing `?? 0` defaulting of `oldBeads` / `oldAntibodies` for pre-Phase-15 runs. Two new integration tests (`calculator.integration.test.ts` Group L at lines 1075-1218) prove both the happy-path restore (T-L1, both flags true) and the legacy fallback (T-L2, both flags absent → ?? false default), each with pre-mutation to confirm the restore is active (not coincident with initial state).

No bugs, security issues, or warnings were found. Four Info-level observations are recorded below — minor polish items that do not block Phase 16 build.

### IN-02: WR-02 IPC-null-result test asserts fewer fields than the IPC-throw test

**File:** `src/renderer/src/features/run/hooks/__tests__/useRunSnapshot.test.ts:260-279`
**Issue:** The IPC-throw test (lines 223-258) exhaustively asserts that all 10 conditionally-spread fields are `undefined` (sapeName, sapeConcentration, beadsDiluent, antibodiesDiluent, beadsVolumePerWell, antibodiesVolumePerWell, premixConcentration, oldBeadsOverride, oldAntibodiesOverride, calculationRulesVersion). The companion IPC-null-result test (lines 260-279) only asserts on `calculationRulesVersion` and `sapeName`. Both branches share the same `auditTrailCaptured = false` gate, so the omission is correct in practice, but the test is thinner than its sibling and would not catch a regression where only ONE branch starts incorrectly writing a subset of the 10 fields.

### IN-04: Pre-existing `deriveDiluentBranchLabel` does not branch on `kind === 'legacy'` even though the docstring lists it

**File:** `src/renderer/src/features/run/lib/auditTrail.ts:43-60`
**Issue:** The function's docstring (lines 43-47) enumerates four cases and explicitly maps `diluent.kind === 'legacy'` → `'Per-reagent fallback (no premix selected)'`. The implementation, however, only inspects `diluent.kind === 'premix'` and then branches on `premixConcentration`. For the `legacy` kind, the function returns `'no premix selected'` only when `premixConcentration === null`; if `premixConcentration` is non-null (which is the well-formed case for a Phase-15 save), the function returns `'no 1× premix in selection'` — contradicting the docstring's stated mapping.

This is **pre-existing Phase 15 code, not introduced by Phase 15.1**, and is therefore out of scope for the 15.1 gap-closure sweep. Flagging here because the review request scoped `auditTrail.ts` and the misalignment between docstring and code is observable in this file. The branch is reachable only when `resolveDiluent` returns `kind: 'legacy'` (i.e., neither a premix nor a valuesTable was provided), which in practice requires a pre-SMK3-08 panel — these are being eliminated by Phase 13 per the comment in `diluent.ts:17`. Risk is therefore low for v1.0.0 but should be tracked.
**Fix (deferrable to v1.0.1):** Explicitly handle the legacy kind so the implementation matches the docstring:
```ts
export function deriveDiluentBranchLabel(
  diluent: DiluentResult,
  premixConcentration: number | null
): string {
  if (diluent.kind === 'premix') {
    return `Concentration-keyed (${diluent.name} @ 1× wins)`
  }
  if (diluent.kind === 'legacy' || premixConcentration === null) {
    return 'Per-reagent fallback (no premix selected)'
  }
  return 'Per-reagent fallback (no 1× premix in selection)'
}
```

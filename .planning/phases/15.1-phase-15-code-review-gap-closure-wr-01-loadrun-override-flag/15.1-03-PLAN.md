<objective>
WR-01: Restore `oldBeadsOverride` and `oldAntibodiesOverride` into `calculatorStore` during `runStore.loadRun` (TWO sites — store cascade + form-side mirror useEffect), so reopening a run that was saved with override-accepted values shows the override badge on the form AND does not re-trigger the cap modal on first interaction. Per D-15.1-03/04: write path already works (Phase 15-01 columns + Phase 15-03 packs them); the gap is purely on the read path.

Purpose: Close WR-01 from `15-REVIEW.md`. The current `runStore.loadRun` cascade at lines 142-159 restores `volumePerWell`, `numberOfSetups`, `oldBeads`, and `oldAntibodies` but skips the two Phase-15 override flags. Result: reopening a saved-with-override run shows the OVERRIDE chip in the audit trail (reads `RunRecord.oldBeadsOverride` directly) but loses the amber "overridden" badge on the calculator form input — and the cap modal re-triggers on first interaction (because `CalculatorForm.tsx`'s local React state at lines 76-77 starts at `false` regardless of the store flag value).

Per Pitfall 2 in RESEARCH.md (and 15-REVIEW.md:99-103 "alternative fix"), this is a TWO-site fix:
1. `runStore.loadRun` — add 2 setter calls AFTER `setOldAntibodies` (the store side).
2. `CalculatorForm.tsx` — subscribe to the 2 store flags + add 2 useEffects that mirror them into local React state on every change (the form side). Without #2, the cap modal still re-triggers because local `beadsOverrideAccepted` is stale.

Output: 2 new lines in `runStore.loadRun`; 4 new lines (2 subscriptions + 2 useEffects) in `CalculatorForm.tsx`; new Group L describe in `calculator.integration.test.ts` with 2+ cases locking the store-side round-trip.

<domain>
## Phase Boundary

Close three Phase 15 code-review warnings that affect audit-trail integrity and round-trip fidelity, so v1.0.0 ships with a complete and consistent audit trail. This is a tactical fix sweep, **not** a feature phase — no new requirements, no new behavior, no new tests beyond regression coverage of the three fixes.

**In-scope:**
1. **WR-02 fix (audit-trail integrity):** `buildRunSnapshot` MUST NOT silently swallow `getWithReagents` returning null. When the IPC fails or the master panel is missing, either surface a user-facing error OR skip writing `calculationRulesVersion='smoke3'` (treat as legacy custom-assay save). A run saved with `calculationRulesVersion='smoke3'` but empty audit-trail fields is data corruption from the audit-trail render's perspective.
2. **WR-01 fix (round-trip fidelity):** `runStore.loadRun` (or wherever the load cascade lives) restores `oldBeadsOverride` and `oldAntibodiesOverride` from the persisted `RunRecord` into `calculatorStore`, so reopening a saved run shows the override-badge state on the form (currently it only shows in the audit trail, creating a UX inconsistency).
3. **WR-06 fix (audit-trail completeness):** Derive the 6 hardcoded `—` rows in `AuditTrailSection` (Raw bead/antibody volume, New beads/antibodies, Total bead/antibody volume) from the snapshot data + existing calculator helpers (`calculateTotalWells`, `calculateRawVolume`, `calculateFinalVolume`, etc.). No new persisted fields needed — these are computed from already-snapshotted values + the old-reagent subtraction pipeline. The derivation steps are in `15-REVIEW.md` WR-06 analysis.

**Out-of-scope:**
- New requirements / new SMK3-XX rules
- New version marker (all three fixes ship behind the existing `'smoke3'` `calculationRulesVersion` — legacy runs are unaffected)
- UI redesign of the audit-trail section (still 4 blocks, still same ordering)
- Refactoring the snapshot builder beyond the WR-02 fix (the async / IPC structure stays)
- Phase 15's deferred items (any "wouldn't it be nice if…" goes to v1.0.1 or v1.1)
- Re-running `/gsd-code-review` as a gate (15.1 is a tactical sweep; if rerun is desired, it's after-the-fact)

**Hard precondition (for Phase 16):** Phase 15.1 MUST be merged and `[x]` in ROADMAP before Phase 16 runs `npm run build:win`. Phase 16's plan will verify this gate.

<decisions>
## Implementation Decisions

### WR-02 — silent-null on getWithReagents

- **D-15.1-01:** **Pick "skip the smoke3 marker" over "surface an error."** When `getWithReagents` returns null (or the IPC fails), `buildRunSnapshot` does NOT set `calculationRulesVersion = 'smoke3'` and does NOT pack the 10 audit-trail fields. The run saves as a legacy custom-assay-style save (no marker, no snapshot fields). Rationale:
  - The user's flow is "save the run" — blocking the save because a master-panel lookup failed is hostile UX for an edge case.
  - The audit-trail render already handles missing snapshot fields (em-dash + historical-run banner per SMK3-16). So a silently-legacy-saved run renders correctly; the inconsistency we're fixing is "smoke3 marker set but snapshot empty."
  - **However** — the silent-skip MUST be logged via the existing log infrastructure (`console.warn` or `electron-log` if available) so a future operator/developer can diagnose "why didn't this run get an audit trail?"
- **D-15.1-02:** Add an explicit boolean gate in `buildRunSnapshot`: only write `calculationRulesVersion` AND the 10 snapshot fields when the master-panel + reagents lookup succeeded. Both happen together or neither. No partial writes.

### WR-01 — loadRun doesn't restore override flags

- **D-15.1-03:** **Restore both `oldBeadsOverride` and `oldAntibodiesOverride` into `calculatorStore` during the load cascade.** The persisted `RunRecord` already carries both fields (Phase 15-01 added the columns; Phase 15-03 packs them). The fix is purely on the read path — read both flags from `RunRecord` and call the appropriate `calculatorStore` setters during load.
- **D-15.1-04:** The load-cascade entry point is `runStore.loadRun` (per `15-REVIEW.md` WR-01 analysis). The fix sets the flags BEFORE the `useRunSnapshot` re-derivation runs, so the form-side override badge is visible on reopen without a re-render race.

### WR-06 — 6 hardcoded em-dashes in audit-trail

- **D-15.1-05:** **Derive the 6 missing values, do not add new snapshot fields.** The values are computable from already-snapshotted data:
  - **Raw bead volume** = `calculateRawVolume(totalWells, snapshotBeadsVolumePerWell, snapshotDeadVolume)`
  - **Raw antibody volume** = `calculateRawVolume(totalWells, snapshotAntibodiesVolumePerWell, snapshotDeadVolume)`
  - **New beads** = max(0, ceiling(raw bead volume − persisted Old Beads value, 0.1mL)) — applies the same ceiling-rounding rule as the live calculator
  - **New antibodies** = max(0, ceiling(raw antibody volume − persisted Old Antibodies value, 0.1mL))
  - **Total bead volume** = New beads + persisted Old Beads
  - **Total antibody volume** = New antibodies + persisted Old Antibodies
- **D-15.1-06:** The derivation lives in `src/renderer/src/features/run/lib/auditTrail.ts` (extending the existing helpers added in Phase 15-04), NOT inline in `AuditTrailSection.tsx`. Keeps the pure-helper boundary that Group N already enforces, and lets vitest unit-test the derivation without React.
- **D-15.1-07:** Edge cases handled in the helper:
  - When `volumePerWell` is 0 / NULL (e.g., custom-assay or legacy row): return `null` from the helper, and `AuditTrailSection` renders em-dash (matching SMK3-16 historical-run behavior).
  - When the old-reagent value exceeds the raw volume (overrides can produce this): clamp to 0 (negative New volumes are not physical).
- **D-15.1-08:** New vitest cases under the existing `auditTrail.test.ts` file (Group P — "derived audit-trail rows"): happy path (1 case per of the 6 derivations matching PRD worked example), legacy/null path (1 case proving em-dash render), override-clamp path (1 case proving 0 on negative).

### Plan structure (Claude's Discretion)

- 15.1 is a tactical sweep. Reasonable plan options: single plan bundling all three fixes + tests, OR 3 plans (one per WR) executed sequentially. Recommend single plan — the three fixes touch disjoint files (snapshot builder, loadRun cascade, audit-trail helpers) so there's no shared-state risk, and bundling keeps the commit history scoped to one logical change ("Phase 15 audit-trail integrity fix").
- Planner's call: 1 plan vs 3. Bundling is faster; splitting gives clearer commit-level traceability.

</decisions>

<specifics>
## Specific Ideas

- **D-15.1-01** decision rationale: "skip the marker" beats "surface an error" because the audit-trail render already handles missing snapshot data gracefully (em-dash + banner). The fix is to make the SAVE side consistent with what the READ side already understands.
- All three fixes share a single `calculationRulesVersion = 'smoke3'` marker — no version bump to `'smoke3.1'`. Legacy `smoke3`-marked runs continue to render correctly because the 10 snapshot fields are unchanged; we're only adding derivation of the 6 em-dashed rows for ALL `smoke3` runs (the derivation is read-side, doesn't affect persisted data).
- The 6 derived audit-trail rows are computed from data the snapshot already captures (`beadsVolumePerWell`, `antibodiesVolumePerWell`, `oldBeads`, `oldAntibodies`, `sampleCount`, `replicateMode`, etc.) — no new DB columns needed. Migration 0009 is final for Phase 15.x.

## Existing Code Insights

### Reusable Assets
- **`calculateTotalWells` / `calculateRawVolume` / `calculateFinalVolume`** (`src/renderer/src/lib/calculator.ts` — exact path verified by researcher) — the pure helpers that the live calculator uses. WR-06 derivation reuses these against snapshot data.
- **Phase 15-04's `auditTrail.ts` helpers** (`computePeVolumeML`, `deriveDiluentBranchLabel`) — establishes the pure-helper pattern that 15.1's WR-06 fix extends. Same file, same test infrastructure.
- **Group M / N test patterns in `auditTrail.test.ts`** — Group P (WR-06 derived rows) follows the same `describe` + happy/null/edge case structure.

### Established Patterns
- **Snapshot fields are nullable in `RunRecord`** (Phase 15-01 D-15-04) — legacy rows have NULL for all 10 fields, smoke3 rows have populated values. WR-06 helpers MUST handle the null case (return null → em-dash) gracefully.
- **`'smoke3'` literal as the rules-version marker** (Phase 15) — single canonical literal, not a constant. WR-03 in `15-REVIEW.md` flags this but is NOT in 15.1 scope (declined). 15.1 keeps using the literal.
- **TDD convention** (Phase 15 plans 03 + 04) — RED → GREEN → REFACTOR commits. 15.1 plans should follow this for the new derivation logic (write tests first, then make them pass).
- **Conditional-write idiom in repositories** (Phase 14-08 / Phase 15-01) — applies to WR-02 fix only if it propagates to the write path. It probably doesn't (`runStore.saveCurrentRun` → IPC, and the snapshot builder is upstream of the IPC). Researcher should confirm.

### Integration Points
- **WR-02 fix → Phase 16 fixture-coverage audit (D-16-15):** The fixture audit for the historical-run banner test (item #2) verifies that a `calculationRulesVersion=NULL` run renders the banner. WR-02 fix means we'll have fewer of those "silently legacy" rows in production (because we explicitly skip the marker on failure rather than write smoke3 + empty fields). The fixture audit is unaffected.
- **WR-01 fix → Phase 16 Section A reopen-and-verify-snapshot step:** The reopen flow now correctly shows the override badge. Section A Step 8 (reopen-and-verify) becomes more thorough — the planner for Phase 16 should add a sub-bullet "verify override badge appears on reopened form."
- **WR-06 fix → Phase 16 Section B SMK3-15 row:** With the 6 em-dashes derived, the audit-trail render is complete. SMK3-15 row in Section B no longer needs an "ignore the 6 em-dash rows" caveat. Phase 16 plan updates Section B SMK3-15 accordingly.

### Anti-patterns to Avoid
- **Don't change the snapshot schema.** Migration 0009 is final. WR-06 derives values; it doesn't persist them.
- **Don't introduce a new `calculationRulesVersion` marker.** All three fixes ship under `'smoke3'`. Bumping to `'smoke3.1'` would mean legacy `'smoke3'` runs render differently — that's a regression.
- **Don't refactor the snapshot builder beyond the WR-02 fix.** WR-02 needs one boolean gate; nothing else. Avoid scope creep into "while we're in there" cleanup.
- **Don't add `console.error` paths that crash the save flow on IPC failure.** Per D-15.1-01, silent-skip is the policy; log a warning, don't throw.

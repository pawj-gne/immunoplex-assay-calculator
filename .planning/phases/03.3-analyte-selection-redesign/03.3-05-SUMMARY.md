## Decisions Made

Initial feat:
- **Two-phase transition:** Keep outgoing page mounted (absolutely positioned, exit animation) alongside incoming page (normal flow, enter animation) for 300ms. Simpler than a route-style animation primitive and plays well with tw-animate-css.
- **Navigation outside the transition container:** Previous/Next buttons do not animate, avoiding jitter and keeping focus stable.
- **plateStore is source of truth:** `useWellSelection.onSelectionChange` dispatches `setWellRange` / `toggleWell`; the hook itself owns no selection state.

Post-approval fixes (the non-obvious decisions forced by human verification):
- **Race condition in finalizeDrag:** The setState callback used to finalize a drag runs async, so refs had to be captured into local variables *before* being reset - otherwise the callback saw cleared state.
- **Visual source of truth in interactive mode:** `usePlateLayout` labels wells by role (standard/unknown/empty) based on static layout. Once the plate is interactive, the displayed "filled-ness" and sample number must come from the plateStore selection set plus a dynamic index, not from `well.type`. This affected both clear-plate appearance and numbering on manually-added plates.
- **`UNKNOWN_WELLS_DUPLICATES` is already a sample count, not a well count:** Dividing by the replicate factor again yielded half the correct capacity in duplicates mode. Fixed at the source.
- **Order-of-operations in calculatorStore:** Capacity validation after mode change must run against the freshly-recalculated plate count, which means propagating to plateStore before validating.
- **Guard against over-assignment:** PlatePanel now rejects 'add' actions when `samplesRemaining <= 0` rather than silently allowing an invalid state.

## Deviations from Plan

**Plan shape vs reality:** The plan defined two tasks (feature build + human-verify). The feature shipped in one `feat` commit (`4ea29e1`), but human verification surfaced five distinct bugs across UI state, hook timing, store ordering, and math - each fixed in its own `fix` commit over the following ~52 minutes. The plan did not anticipate this tail, and the fixes touch files beyond the plan's declared `files_modified` (PlateGrid, WellCell, useWellSelection, calculator.ts, calculatorStore.ts).

This is not a failure of the plan - the human-verify gate is precisely where these would be expected to surface - but the two-task structure under-represents the actual work. The fixes are listed explicitly above under "Post-approval fixes" so downstream readers can trace what changed after the feat landed.

**Total deviations:** 5 post-approval fix commits beyond the planned feat. All were in-scope bug fixes required to satisfy the plan's success criteria (interactive plate functional, duplicates mode correct, sample numbering correct across plates).

## Issues Encountered

All issues were discovered during the human-verify checkpoint and resolved in the five fix commits listed above:

- Drag selection occasionally "lost" its action at the end of a drag (ref reset vs async setState) - fixed in `33f22fa`
- "Clear Plate" left wells looking selected because unselected wells in interactive mode inherited the layout's green - fixed in `33f22fa`
- Duplicates mode showed 18 samples/plate instead of 36 due to a double-division in `calculateMaxSamples` - fixed in `cd2d84f`
- Switching replicate mode validated capacity against a stale plate count - fixed in `cd2d84f`
- Deselected wells kept showing their old sample numbers - fixed in `4039cc6`
- User could select past the sample-count ceiling - fixed in `4039cc6`
- Manually-added plates showed blank wells because `usePlateLayout` marked them as `empty` - fixed in `1a76688` and `b6b1f67`
